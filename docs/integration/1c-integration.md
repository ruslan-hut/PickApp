# Посібник інтегратора 1С

Цей документ описує, як обліковій системі (1С) обмінюватися даними з сервером Pick,
який обслуговує термінали збору даних (ТЗД) на Android.

Супутній документ: [Чекліст інтегратора](1c-checklist.md) — покроковий порядок запуску.

> Документ актуалізується разом зі змінами контракту REST API. Якщо ви бачите
> розбіжність із поведінкою сервера — контракт змінився, повідомте розробника.

---

## 1. Загальна схема

```
   1С  ──REST /api/v1──▶  сервер Pick  ──REST /device──▶  Android ТЗД
        ◀── результати ──               ◀── сканування ──
```

- 1С **завантажує** довідники, працівників і документи на сервер.
- Термінал **отримує** те, що йому належить, за ролю, складом і каналом продажу.
  Термінал нічого не вирішує сам — усі правила визначає сервер за даними від 1С.
- 1С **забирає** оброблені документи і підтверджує отримання.

Термінал — тонкий шар відображення. Якщо потрібно змінити його поведінку,
змінюють дані, які надсилає 1С, а не програму на терміналі.

---

## 2. Автентифікація

Кожен запит містить заголовок з токеном орендаря (tenant):

```
X-API-Key: <токен, виданий адміністратором Pick>
```

Токен однозначно визначає орендаря — окремо передавати ідентифікатор
організації не потрібно.

Базова адреса: `https://<host>:<port>/api/v1`

Необов'язковий заголовок `X-Erp-Actor: Іванов І.І.` дозволяє записати в журнал
змін, хто саме в 1С ініціював операцію. Без нього автором буде «ERP».

---

## 3. Ключовий принцип: `external_id`

**Усі сутності, що походять з 1С, ідентифікуються GUID-ом 1С** (`external_id`).
Внутрішні ідентифікатори бази Pick назовні ніколи не виходять.

`external_id` використовується:

- у параметрах URL: `GET /api/v1/documents/{external_id}`;
- у полях-посиланнях: `warehouse_id`, `client_id`, `product_id`,
  `assigned_worker_id`, `box_id`;
- у відповідях сервера.

```
GET /api/v1/products/8888e07f-e948-11ef-b803-00155d018000
GET /api/v1/users/ERP-USER-001
```

Формат довільний — GUID 1С, код, будь-який стабільний рядок. **Головне —
незмінність.** Якщо `external_id` товару зміниться, сервер вважатиме це новим
товаром, а рядки старих документів «зависнуть» без прив'язки.

---

## 4. Порядок первинного завантаження

Завантажуйте довідники до документів — документ посилається на них і буде
відхилений, якщо посилання не резолвиться.

1. Склади — `POST /api/v1/warehouses/batch`
2. Товари — `POST /api/v1/products/batch`
3. Контрагенти — `POST /api/v1/clients/batch`
4. Коробки (за потреби, для етапу пакування) — `POST /api/v1/boxes/batch`
5. Працівники — `POST /api/v1/users/batch`
6. Документи — `POST /api/v1/documents/batch`

Усі `/batch` — це upsert: збіг за `external_id` оновлює запис, інакше створює.

## 5. Товари і штрихкоди

```http
POST /api/v1/products
Content-Type: application/json
X-API-Key: ...

{
  "external_id": "8888e07f-e948-11ef-b803-00155d018000",
  "code": "T-0042",
  "name": "Горілка «Приклад» 0,5 л",
  "unit": "шт",
  "supports_batches": false,
  "is_active": true,
  "barcodes": [
    { "barcode": "4820000000017", "type": "EAN13", "is_primary": true },
    { "barcode": "0104820000000017", "type": "GS1_DATAMATRIX", "is_primary": false }
  ]
}
```

| Поле | Вплив на роботу термінала |
| --- | --- |
| `barcodes[]` | За цими кодами термінал знаходить товар при скануванні у звичайних документах. Один товар може мати кілька кодів. |
| `type` | `EAN13`, `EAN8`, `GS1_DATAMATRIX`, `QR`. |
| `is_primary` | Не більше одного на товар. Довідковий, на пошук не впливає. |
| `unit` | Показується в рядку документа. |
| `supports_batches` | Вмикає введення партії/серії на рядку. |
| `is_active` | `false` — товар лишається в базі, але вважається неактивним. |

> Для документів Е-Акцизу штрихкоди товару **не використовуються** — там працюють
> штрихкоди рядка документа (розділ 9).

## 6. Працівники та режими роботи термінала

```http
POST /api/v1/users

{
  "external_id": "ERP-USER-001",
  "login": "worker1",
  "password": "securepassword",
  "name": "Іваненко Іван",
  "role": "COLLECTOR",
  "only_assigned_docs": false,
  "sales_channel": "B2B",
  "available_document_types": [
    { "code": "OUTGOING_SHIPMENT", "description": "Відвантаження" },
    { "code": "INCOMING_RECEIPT",  "description": "Прийом товару",
      "allows_over_plan": true, "allows_extra_lines": true },
    { "code": "EXCISE", "description": "Е-Акциз" }
  ]
}
```

### Ролі

| Роль | Що бачить |
| --- | --- |
| `COLLECTOR` | Етапи «Збірка» і «Пакування». Спочатку документи на пакування, потім на збірку. |
| `COURIER` | Лише етап «Доставка». |
| `ADMINISTRATOR` | Усі документи. |

### `available_document_types` — головний важіль керування терміналом

Це **єдине місце**, де задається людська назва типу документа. Термінал показує
`description` як кнопку режиму роботи на головному екрані; `code` має точно
збігатися зі значенням `type` у документі.

Прапорці — тристанні: **не передавати** = взяти типове значення термінала;
передати `true`/`false` = примусово задати поведінку.

| Прапорець | Типове | `true` | `false` |
| --- | --- | --- | --- |
| `allows_over_plan` | `false` | Можна набрати більше плану. | Сканування і ручне введення обмежені планом; надлишок відхиляється. |
| `allows_extra_lines` | `false` | Сканування товару, якого немає в документі, **створює новий рядок**. | Невідомий скан → повідомлення «товару немає в документі». Перелік рядків закритий. |
| `requires_plan` | `true` | Показуються «План:», індикатори прогресу. | План приховано, перевірки надлишку вимкнено. |

### Інші поля

| Поле | Вплив |
| --- | --- |
| `only_assigned_docs` | `true` — працівник бачить лише документи, де він указаний у `assigned_worker_id`. |
| `sales_channel` | `B2B` / `B2C` / порожньо. Якщо задано, працівник бачить документи свого каналу **або без каналу**. Порожньо = бачить усі. Пропуск поля зберігає попереднє значення. |

Склад працівника задається **окремим запитом** — у `POST /api/v1/users` поля
`warehouse_id` немає:

```http
PUT /api/v1/users/ERP-USER-001/warehouse

{ "warehouse_id": "ERP-WH-001" }
```

Склад визначає, з якої черги працівник отримує документи. `null` — відв'язати.

## 7. Документи

```http
POST /api/v1/documents

{
  "external_id": "7f7b315c-1b8c-11f1-9d91-0cc47a39a0b3",
  "version": "0x00000000000A1B2C",
  "type": "OUTGOING_SHIPMENT",
  "number": "РН-2026-00123",
  "date": "2026-07-09T00:00:00Z",
  "client_id": "1bd6f37f-a3fd-11ee-b7b0-00155d018000",
  "warehouse_id": "ERP-WH-001",
  "assigned_worker_id": "ERP-USER-001",
  "sales_channel": "B2B",
  "priority": false,
  "requires_pack_stage": true,
  "requires_review": false,
  "notes": "Обережно, скло",
  "lines": [
    {
      "line_number": 1,
      "product_id": "8888e07f-e948-11ef-b803-00155d018000",
      "planned_quantity": 100,
      "volume": 500,
      "volume_unit": "ml",
      "location_path": "Ряд 3 / Полиця 2"
    }
  ]
}
```

Документ створюється у стані `LOADED`.

### Поля заголовка і їх вплив

| Поле | Обов'язкове | Вплив на роботу термінала |
| --- | --- | --- |
| `external_id` | так | Ключ документа. Повторний `POST` з тим самим значенням = оновлення. |
| `type` | так | Довільний рядок. Сервер не перевіряє. Має збігатися з `code` у `available_document_types` працівника, інакше працівник документа не побачить. |
| `number`, `date` | так | Показуються у списку; `date` задає порядок у черзі. |
| `warehouse_id` | так | Визначає, чия це черга. |
| `client_id` | ні | Назва контрагента у шапці документа. |
| `assigned_worker_id` | ні | Документ бачить лише цей працівник. 1С — джерело істини: кожне оновлення перезаписує призначення. |
| `priority` | ні | `true` — документ спливає на початок черги. Пропуск поля зберігає попереднє значення. |
| `sales_channel` | ні | `B2B` / `B2C` / порожньо. Фільтрує чергу за каналом працівника. |
| `requires_pack_stage` | ні | `true` — після збірки документ автоматично переходить на етап пакування (коробки). Для типів без доставки лишайте `false`. |
| `requires_review` | ні | `true` — якщо після збірки план ≠ факт, документ паркується у стані `REVIEW` і чекає на рішення менеджера в 1С. |
| `notes` | ні | Примітка **до документа**, показується працівнику. Не плутати з `lines[].notes`. |
| `tracking_number` + `shipping_connection_code` | ні | ТТН перевізника. Передаються тільки разом. |
| `version` | ні | Довільний токен змін (наприклад `rowversion`). Якщо збігається зі збереженим — сервер нічого не пише і повертає «без змін». Порівнюється **лише на рівність**, не впорядковується. |

### Поля рядка

| Поле | Власник | Примітка |
| --- | --- | --- |
| `line_number` | 1С | Додатний, унікальний у межах документа. Задає порядок відображення. |
| `product_id` | 1С | `external_id` товару. `product_code`, `product_name`, `unit` підтягуються з довідника — **не передавайте їх**. |
| `planned_quantity` | 1С | План. Не може бути від'ємним. |
| `volume`, `volume_unit` | 1С | Фізичний об'єм одиниці (напр. `500` + `"ml"`). Термінал сортує рядки за `volume` зростанням. |
| `location_id`, `location_path` | 1С | Адреса зберігання, показується в рядку. |
| `expiration_date` | 1С | Термін придатності. |
| `barcodes` | 1С | Штрихкоди рядка. Див. розділ 9. |
| `actual_quantity` | **працівник** | Факт. Можна передати на новому документі (`LOADED`), далі — не чіпається. |
| `batch_number` | **працівник** | Партія/серія. |
| `is_completed` | **працівник** | Ознака «рядок закрито». |
| `notes` | **працівник** | Примітка працівника до рядка. **1С не може її задати** — надіслане значення ігнорується. |
| `has_photo` | **працівник** | Тільки для читання. Фото забирається окремим запитом. |

### Правило збереження даних працівника

Поки працівник тримає документ у роботі (стани `COLLECTING` / `PACKING` /
`DELIVERING`), прапорець `erp_sync_blocked` = `true`, і будь-яке оновлення з 1С
повертає **`409 Conflict`**. Це не помилка інтеграції — це захист. Повторіть
спробу пізніше.

Після зняття блокування 1С може оновлювати документ, але поля з таблиці вище,
позначені «працівник», **завжди зберігаються** зі старої версії. Так само
повністю зберігається масив `boxes`. `total_planned` / `total_actual`
перераховуються сервером із підсумкових рядків.

## 8. Життєвий цикл документа

```
                LOADED ──▶ COLLECTING ──▶ COLLECTED ──┬──▶ SENT
 (створено 1С)   збірка:  взято в роботу   зібрано     │  (1С підтвердила)
                                                       │
                                       requires_pack_stage
                                                       ▼
                  PACK ──▶ PACKING ──▶ PACKED ──▶ DELIVERY ──▶ DELIVERING
                                                                    │
                                                                    ▼
                                                               DELIVERED ──▶ SENT
```

- `REVIEW` — «парковка» поза етапами: документ із `requires_review: true`, у якого
  після збірки план ≠ факт. Знімається рішенням 1С
  (`POST /api/v1/documents/{id}/review`: `approve` або `recollect`).
- `ERROR` — аварійний стан.
- Переходи між етапами робить сервер або 1С, не термінал.

## 9. Штрихкоди рядка документа та Е-Акциз

### Навіщо

У звичайному документі рядок — це «товар × кількість», і сканування шукає товар
у довіднику за штрихкодом. В українській системі електронного акцизу
(**Е-Акциз**) кожна пляшка/пачка має **унікальну е-марку**, тож рядок документа
відповідає **одному фізичному екземпляру**. Заводити картку товару на кожну
марку неможливо.

Тому рядок документа може нести **власні коди сканування** — поле `barcodes`.

### Правила

- `barcodes` — масив рядків, належить 1С, перезаписується при кожному
  довантаженні документа.
- Сканування шукає збіг **по всіх рядках документа**, а не по першому знайденому.
- Один і той самий код у кількох рядках = **код групової упаковки**: сканування
  закриває всі ці рядки одночасно.
- Збіг за `barcodes` має **пріоритет** над пошуком товару за штрихкодом. Якщо
  жоден рядок не збігся — термінал шукає товар у довіднику, як завжди.
- Знайдені рядки отримують `actual_quantity = planned_quantity` і
  `is_completed = true`. Повторне сканування нічого не змінює.
- **`barcodes[0]` має бути унікальним у межах документа** — сервер використовує
  його як ключ, щоб зберегти роботу комірника при повторному довантаженні
  документа з 1С. Ставте туди код самої марки. Код пачки — другим елементом.
- Порожнє поле = звичайна поведінка. Старі документи не змінюються.

### Приклад: документ Е-Акцизу

Три пляшки одного SKU; перші дві лежать у пачці `GRP-000417`.

```http
POST /api/v1/documents

{
  "external_id": "ERP-EXC-0001",
  "type": "EXCISE",
  "number": "ЕА-2026-0001",
  "date": "2026-07-09T00:00:00Z",
  "warehouse_id": "ERP-WH-001",
  "lines": [
    { "line_number": 1, "product_id": "SKU-VODKA-05", "planned_quantity": 1,
      "barcodes": ["ABC000000001XYZ", "GRP-000417"] },
    { "line_number": 2, "product_id": "SKU-VODKA-05", "planned_quantity": 1,
      "barcodes": ["ABC000000002XYZ", "GRP-000417"] },
    { "line_number": 3, "product_id": "SKU-VODKA-05", "planned_quantity": 1,
      "barcodes": ["ABC000000003XYZ"] }
  ]
}
```

Поведінка на терміналі:

| Комірник сканує | Результат |
| --- | --- |
| `ABC000000003XYZ` | Закривається рядок 3. |
| `GRP-000417` | Закриваються рядки 1 і 2 разом. |
| `GRP-000417` вдруге | Нічого не змінюється, повідомлення «вже зібрано». |
| штрихкод товару `SKU-VODKA-05` | «Товару немає в документі» — бо `allows_extra_lines: false`. |

### Обов'язкове налаштування типу

Щоб комірник міг лише **підтверджувати** надіслані марки, а не додавати свої,
тип `EXCISE` у працівника має бути описаний так:

```json
{ "code": "EXCISE", "description": "Е-Акциз" }
```

Прапорці не передаються — типові значення (`allows_extra_lines: false`,
`allows_over_plan: false`, `requires_plan: true`) саме те, що потрібно.
`description` — це те, що комірник побачить на кнопці режиму.

### Що передавати в `barcodes[0]`

Унікальний ідентифікатор е-марки — той самий рядок, який зчитується з
DataMatrix-коду на одиниці товару. Термінал порівнює **точно**, з урахуванням
регістру, без нормалізації. Передавайте рівно те, що потрапить у сканер.

### Що комірник бачить у рядку

Назва товару береться з картки товару (`products.name`) і **однакова в усіх
рядків** е-акцизного документа — порядково її задати не можна. Тому в підзаголовку
рядка термінал показує **`barcodes[0]`** замість коду товару: це єдине, що
розрізняє рядки.

```
Горілка «Приклад» 0,5 л
ABC000000001XYZ                    0 / 1
```

Отже: щоб змінити напис у рядку, редагують `name` картки товару; щоб змінити
підзаголовок — передають інший `barcodes[0]`.

## 10. Отримання результатів у 1С

1. **Забрати оброблені документи:**

   ```
   GET /api/v1/documents/completed
   ```

   Повертає документи у стані `DELIVERED` (пройшли кур'єра) або `COLLECTED`
   (без етапу доставки). У відповіді — фактичні кількості, партії, примітки
   працівника, ознаки фото і масив `boxes` із фінальними статусами.

2. **Підтвердити отримання:**

   ```
   POST /api/v1/documents/{external_id}/acknowledge
   ```

   Документ переходить у `SENT`. Для `OUTGOING_SHIPMENT` приймається лише
   стан `DELIVERED`.

3. **Фото рядка (за потреби):**

   ```
   GET /api/v1/documents/{external_id}/lines/{line_number}/photo
   ```

4. **Прибрати неактуальні документи:**

   ```
   POST /api/v1/documents/sync
   ```

   Передайте повний перелік `external_id` активних документів. Документи у стані
   `LOADED`, яких немає в переліку, будуть видалені. Документи в роботі не
   чіпаються. Викликайте одразу після `POST /api/v1/documents/batch`.

## 11. Помилки

| Код | HTTP | Що робити |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | У відповіді — перелік полів і причин. Виправити дані. |
| `UNAUTHORIZED` | 401 | Перевірити `X-API-Key`. |
| `NOT_FOUND` | 404 | Посилання (`product_id`, `warehouse_id`…) не резолвиться. |
| `DOCUMENT_LOCKED` | 409 | Документ у роботі (`erp_sync_blocked: true`). Повторити пізніше. |

Успішна відповідь загорнута в конверт `{"status": "ok", "data": ...}`,
помилка — `{"status": "error", "error": {...}}`.

## 12. Типовий регламент обміну

| Періодичність | Дія |
| --- | --- |
| Разово при впровадженні | Склади, коробки, працівники |
| Раз на добу / за зміною | `POST /products/batch`, `POST /clients/batch` |
| Кожні 5–15 хв | `POST /documents/batch` → `POST /documents/sync` |
| Кожні 5–15 хв | `GET /documents/completed` → `POST /documents/{id}/acknowledge` |
| За потреби | `GET /documents?state=REVIEW` → `POST /documents/{id}/review` |

Використовуйте поле `version` на документах і товарах: якщо токен не змінився,
сервер не робить запису, і обмін лишається дешевим навіть при повному вивантаженні.
