# Чекліст інтегратора 1С

Покроковий порядок запуску обміну між 1С і сервером Pick.
Деталі кожного кроку — у [Посібнику інтегратора](1c-integration.md).

Позначайте кроки по мірі виконання. Кроки йдуть у порядку залежностей:
не переходьте до наступного, поки попередній не дає `200`/`201`.

---

## Крок 0. Доступ

- [ ] Отримано адресу сервера (`https://<host>:<port>`).
- [ ] Отримано токен орендаря; він передається в заголовку `X-API-Key`.
- [ ] `GET /health` повертає `200`.
- [ ] Тестовий запит `GET /api/v1/warehouses` повертає `200` (порожній перелік — нормально).

## Крок 1. Домовитися про ідентифікатори

- [ ] Обрано джерело `external_id` для кожної сутності (GUID 1С або код).
- [ ] Перевірено, що ці значення **не змінюються** протягом життя об'єкта.
- [ ] Для складів/користувачів, яких немає в 1С як об'єктів, узгоджено сталі коди
      (`ERP-WH-001`, `ERP-USER-001`).

## Крок 2. Склади

- [ ] `POST /api/v1/warehouses/batch` — вивантажено всі склади.
- [ ] `GET /api/v1/warehouses` — перелік збігається з 1С.

## Крок 3. Товари

- [ ] `POST /api/v1/products/batch` — вивантажено товари.
- [ ] У кожного товару заповнено `barcodes` (крім товарів, що беруть участь лише
      в документах Е-Акцизу).
- [ ] `unit` заповнено — він показується комірнику.
- [ ] `supports_batches` виставлено для товарів, де потрібна партія/серія.
- [ ] Перевірено: `GET /api/v1/products/{external_id}` повертає очікувані штрихкоди.

## Крок 4. Контрагенти

- [ ] `POST /api/v1/clients/batch`.

## Крок 5. Коробки (лише якщо буде етап пакування)

- [ ] `POST /api/v1/boxes/batch`.
- [ ] У коробок-місць доставки виставлено `is_parcel: true` (для них комірник
      вводить вагу), у вкладених — `false`.

## Крок 6. Працівники і режими роботи

- [ ] `POST /api/v1/users/batch` — створено облікові записи.
- [ ] У кожного вказано `role` (`COLLECTOR` / `COURIER` / `ADMINISTRATOR`).
- [ ] `PUT /api/v1/users/{external_id}/warehouse` — прив'язано до складу.
- [ ] Заповнено `available_document_types`:
  - [ ] `code` кожного запису **точно** дорівнює значенню `type` у документах;
  - [ ] `description` — це напис на кнопці режиму на терміналі
        (наприклад `"Е-Акциз"`);
  - [ ] прапорці `allows_over_plan` / `allows_extra_lines` / `requires_plan`
        виставлені свідомо, або пропущені (тоді діють типові значення:
        план обов'язковий, надлишок і нові рядки заборонені).
- [ ] Якщо потрібен поділ на канали — виставлено `sales_channel` (`B2B` / `B2C`).
- [ ] Працівник увійшов на терміналі та бачить очікувані кнопки режимів.

## Крок 7. Документи

- [ ] `POST /api/v1/documents/batch` — вивантажено активні документи.
- [ ] У кожного документа:
  - [ ] `type` збігається з одним із `code` працівника;
  - [ ] `warehouse_id` — склад, до якого прив'язаний працівник;
  - [ ] `line_number` додатні й унікальні;
  - [ ] `product_id` існують у довіднику;
  - [ ] `lines[].notes` **не передається** (поле належить працівнику).
- [ ] `requires_pack_stage: true` виставлено там, де потрібен етап пакування.
- [ ] `POST /api/v1/documents/sync` — передано повний перелік активних
      `external_id`, щоб прибрати неактуальні документи.
- [ ] Документ з'явився на терміналі в потрібного працівника.

## Крок 8. Документи Е-Акцизу

- [ ] Тип документа заведено у працівника: `{ "code": "EXCISE", "description": "Е-Акциз" }`
      **без прапорців** (потрібні саме типові значення).
- [ ] Кожна е-марка — **окремий рядок** з `planned_quantity: 1`.
- [ ] `barcodes[0]` — унікальний ідентифікатор е-марки, рівно в тому вигляді, в
      якому він зчитується сканером з DataMatrix.
- [ ] `barcodes[1]` — код групової упаковки, **однаковий** для всіх рядків, що
      лежать у цій упаковці. Якщо упаковки немає — елемента немає.
- [ ] `barcodes[0]` унікальний у межах документа (це ключ збереження роботи
      комірника при повторному вивантаженні).
- [ ] Перевірено на терміналі:
  - [ ] сканування коду марки закриває **один** рядок;
  - [ ] сканування коду пачки закриває **всі** рядки цієї пачки;
  - [ ] повторне сканування нічого не змінює;
  - [ ] сканування штрихкоду товару дає «товару немає в документі».

## Крок 9. Забір результатів

- [ ] `GET /api/v1/documents/completed` — документи приходять із фактичними
      кількостями.
- [ ] Дані розкладаються в 1С: `actual_quantity`, `batch_number`,
      `lines[].notes` (примітка комірника), `boxes`.
- [ ] `GET /api/v1/documents/{id}/lines/{n}/photo` — за потреби забираються фото.
- [ ] `POST /api/v1/documents/{id}/acknowledge` — підтверджено отримання
      (документ переходить у `SENT`).

## Крок 10. Обробка помилок

- [ ] `409 DOCUMENT_LOCKED` при оновленні документа **не вважається збоєм** —
      документ у роботі, спробу треба повторити пізніше.
- [ ] `400 VALIDATION_ERROR` логується разом із переліком полів із відповіді.
- [ ] Обмін не падає, якщо один документ із пакета відхилено.

## Крок 11. Регламент

- [ ] Налаштовано періодичність:
  - довідники — раз на добу або за зміною;
  - документи (`batch` + `sync`) — кожні 5–15 хв;
  - забір результатів (`completed` + `acknowledge`) — кожні 5–15 хв.
- [ ] Заповнюється поле `version` (токен змін) на товарах і документах, щоб
      незмінені записи не перезаписувалися.
- [ ] Передається заголовок `X-Erp-Actor` з іменем користувача 1С — для журналу змін.

## Крок 12. Приймальні перевірки перед промисловою експлуатацією

- [ ] Комірник бачить лише свої документи (перевірено з двома працівниками).
- [ ] Повторне вивантаження документа, який комірник уже частково зібрав, **не
      скидає** факт, партії та примітки.
- [ ] Вивантаження документа, який комірник тримає в роботі, повертає `409`.
- [ ] Документ Е-Акцизу: групова упаковка закриває всі свої рядки.
- [ ] Оброблений документ доходить до 1С і отримує `SENT`.
